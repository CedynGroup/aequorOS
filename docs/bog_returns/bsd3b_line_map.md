Generated from `bog_forms/linemaps/bsd3b.py` (= `bsd3a.build_lines("BSD3B", "subsidiary")`) + `layouts/BSD3B.json` (row tables in §3 by the snippet in `bsd3a_line_map.md` §8 with `BSD3B` — do not hand-edit; regenerate).

## 1. What this form is, and what the platform can honestly feed

BSD3B is BSD3A **per subsidiary**: for every subsidiary of the reporting bank, its own twenty largest
depositors, ten largest monetary-sector and fifty largest non-monetary-sector exposures. The map is
therefore BSD3A's map (`bsd3a.build_lines`) in `subsidiary` scope — identical cells, identical
template formulas, identical residual lines — with ONE difference in sourcing:

- **The platform holds no subsidiary register and no subsidiary position book.** Every canonical
  position belongs to the reporting bank's own book (`banks.id`); nothing identifies "subsidiary X's
  depositors". Deriving a subsidiary roster from the bank's own positions would report the parent's
  depositors as the subsidiary's — wrong by construction — so every roster / count cell is
  **input_required** with the note "BSD3-GROUP is required for EACH subsidiary … bank must supply
  per subsidiary". The four numbering constants (`A27:A30` = 22–25) still resolve so the official
  numbering survives the values-only export.
- The moment a subsidiary book exists (a `CO-`/subsidiary entity or an `owning_entity`-scoped
  position slice — see §7), `bsd3a.build_lines("BSD3B", "solo")` applied per subsidiary is the
  complete BSD3B map: no new bindings, no new resolvers (`bsd3.rank` / `bsd3.count` take the slice
  they are given).

Guide rules (items 1–6) and every documented decision are those of `bsd3a_line_map.md` §2 and apply
unchanged once a subsidiary slice is fed.

## 3b. Data-gap closure — subsidiaries register (2026-08-16, documented decision: no roster cell re-pointed)

The **subsidiary register** half of the prerequisite now exists: reference dataset `subsidiaries`
(`docs/data_engine/datasets/subsidiaries.md`; schema `reference_schemas/subsidiaries.py`; one row per
subsidiary per reporting date — identity, ownership, consolidation treatment, the subsidiary's own book,
inter-company balances, minority workings). It fixes WHICH subsidiaries BSD3B must cover, and it feeds BSD9 /
BSD5B. It is **not** a subsidiary position book: a subsidiary's twenty largest depositors / ten largest
monetary-sector / fifty largest non-monetary-sector exposures (names, account types, maturities, currency
splits, on-balance amounts, drawn / undrawn / contingent, security) are position-level facts the register
cannot honestly carry, so **every roster / count cell stays `input_required`** — the note on those cells now
names the register and the missing book (`linemaps/bsd3b.py::SUBSIDIARY_ROSTER_NOTE`; the status split in §2
is unchanged). Design that closes the rest, in the register's key: a `subsidiary_exposures` reference dataset
(one row per `(reporting_date, subsidiary_id, roster ∈ {depositor, monetary_exposure,
non_monetary_exposure}, rank)` with the sheet's fields) read through `refs.field` with
`filters={"subsidiary_id": …, "roster": …}`, `order_by` amount, `index = rank − 1` — or per-subsidiary
canonical positions (§7) with `bsd3a.build_lines("BSD3B", "solo")` applied per subsidiary — **plus**
per-subsidiary emission (§7 ask 1: the catalogue says one workbook PER subsidiary; the generator emits one,
so a `subsidiary_id` filter alone would emit only the first subsidiary). Proof of the decision:
`tests/services/data_gaps/test_subsidiaries.py` (BSD3B binds nothing to the register; the 401 roster / count
cells carry the register-naming note).

## 4. Residual unmapped lines — data the bank must supply

Everything BSD3A lists in its §4 (accrued interest, remarks, value/type of security) PLUS, today,
the rosters themselves — for each subsidiary: the depositor / exposure names, account types,
maturities, foreign / cedi components, on-balance amounts, drawn / undrawn / contingent amounts and
the depositor count. Prerequisite for the platform to feed them: a **subsidiary register** (built
2026-08-16 — reference dataset `subsidiaries`, §3b) and **per-subsidiary canonical positions** or a
`subsidiary_exposures` roster dataset keyed by `subsidiary_id` (ingested under the subsidiary, or tagged
with a subsidiary `owning_entity` that the register recognises).

## 5. Critical checks proven by `tests/services/bog_forms/test_bsd3.py`

1. BSD3B generates through the real package pipeline with `basis == "consolidated"`, no engine
   errors, `unmapped == 0`; `mapped == 4` (row numbers), every other declared cell `input_required`;
2. **the parent's own depositors / exposures never leak into the subsidiary rosters** — every roster
   name cell is blank although the same book makes BSD3A's rosters non-empty;
3. the subsidiary note is carried on exactly the roster + count cells (20×5 + 1 + 10×5 + 50×5);
4. every official cell of the three sheets is declared and unique (shared structural test with BSD3A).

- BSD3B ← BSD3A: same map, same resolvers; the catalogue records the dependency (BSD3A is computed

- Consolidation is Guide §1 (subsidiaries on BSD7B / BSD9 and the GROUP variants BSD3B / BSD5B).

## 7. Framework asks

1. **Subsidiary register + per-subsidiary emission.** The catalogue note says "the workbook is
   emitted once per subsidiary"; the generator emits ONE workbook per return. BSD3B needs (a) a
   subsidiary register on the institution — **built 2026-08-16 as the `subsidiaries` reference
   dataset** (`subsidiary_id`, name, country, entity type, ownership, consolidation method; a
   sibling-entity seam per CLAUDE.md remains the long-run home) — and (b) a generation path that computes the form once per subsidiary over that
   subsidiary's position slice (`ResolveContext` gains a `book`/`entity` scope; `bsd3.rank` /
   `bsd3.count` need no change). Until then BSD3B is structure-only by design.
2. **`owning_entity` as a slice key** — snapshots already carry `owning_entity` (API_INTEGRATION §3.4,
   collateral-management meaning). If BoG-facing group returns are to use it, its semantics must
   be pinned to "legal entity that booked the position" and validated against the register; the
   map deliberately does not infer subsidiary membership from free-text `owning_entity` values.
3. Same asks as `bsd3a_line_map.md` §7 (blank-by-construction status; public canonical slice).
